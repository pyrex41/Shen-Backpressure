# Feature Design Prompt: Mixed-Evidence Report

You are designing a new evidence-reporting layer for Shen-Backpressure. This is a design task, not an implementation task. Produce an implementation-ready design document, but do not edit code.

## Context

Shen-Backpressure already has several kinds of verification evidence, but they are scattered across gate logs, generated files, test output, and audit commands.

Relevant current pieces:

- `cmd/sb/` runs deterministic gates and emits project context.
- `sb.toml` declares target language, spec paths, gate topology, and derive specs.
- `shengen` / `shengen-ts` generate target-language guard types from Shen datatypes.
- `shen-derive` / `shen-derive-ts` generate oracle tests from Shen `(define ...)` functions.
- `sb gates` runs the configured verification pipeline.
- `sb context` emits structured project context for agent prompt hydration.
- `examples/payment/` is the flagship demo.
- `examples/shen-web-tools/` carries the TypeScript derive path.

The problem: users can see whether gates passed, but not what kind of evidence was established. A passing run should produce a durable report answering: what did the tool prove structurally, what did it check by generated samples, what did it only audit for drift, and what remains outside the verified boundary?

## Goal

Design a **Mixed-Evidence Report** that summarizes all verification evidence in a single human-readable and machine-readable artifact.

This is not yet full per-premise proof discharge. Do not overclaim. The v0 report should accurately describe evidence that exists today, while leaving room for future static/runtime per-premise discharge.

## Desired User Experience

A user or agent can run something like:

```bash
sb evidence
sb gates --evidence-out .sb/evidence/current.json
sb context --include evidence
```

And see a concise report:

```text
Verification Evidence

Project:
- lang: go
- spec: specs/core.shen

Structural evidence:
- 8 guard types generated by shengen
- 2 proof-chain constructors require guarded inputs
- generated output matches committed TCB

Oracle evidence:
- processable checked against Shen oracle
- 35 generated cases
- seed: 0
- output: internal/derived/processable_spec_test.go

Target evidence:
- go test ./... passed
- go build ./... passed

Unverified boundary:
- database persistence not described by Shen spec
- HTTP handler wiring covered by ordinary tests only
```

## Design Requirements

### 1. Evidence Taxonomy

Define a concrete taxonomy of evidence kinds.

At minimum consider:

- `shen_typecheck` — Shen spec internal consistency via `tc +`.
- `guard_codegen` — `shengen`/`shengen-ts` generated structural guard types.
- `derive_oracle` — target implementation checked against Shen oracle samples.
- `target_test` — ordinary target-language test command.
- `target_build` — ordinary target-language build/typecheck command.
- `tcb_audit` — generated output drift/tamper check.
- `manual_assumption` — explicit future escape hatch, not v0 unless already present.
- `runtime_assertion` — future category for generated runtime checks.

For each kind, define:

- What input files produce it.
- What command establishes it.
- Whether it is static, sampled, runtime, audit, or unknown strength.
- What failure means.
- What should appear in a human report.
- What should appear in JSON.

### 2. Evidence Schema

Design a JSON schema for `evidence.json`.

Include fields like:

- `schema_version`
- `generated_at`
- `tool_version`
- `project_root`
- `manifest_path`
- `language`
- `specs`
- `items`
- `summary`

Each evidence item should include:

- `id`
- `kind`
- `strength`
- `status`
- `spec_file`
- `target_files`
- `generated_files`
- `command`
- `exit_code`
- `hashes`
- `symbols`
- `sample_count`
- `seed`
- `diagnostics`
- `counterexamples` as references, not necessarily inline details

Be explicit about which fields are required and which are optional.

### 3. v0 Data Sources

Ground the v0 design in current code.

Explain how to collect evidence from:

- `sb.toml`
- `BuildContext(cfg)` / `ProjectContext`
- `buildGateList` / gate execution results
- `[[derive.specs]]`
- shengen output paths
- shen-derive generated output paths
- TCB audit command results
- target test/build gate results

Do not require a new Shen prover or deep AST analyzer for v0.

### 4. Human Output

Design readable markdown output suitable for:

- terminal display
- `sb context --format markdown`
- PR comments
- agent prompt hydration

The report should be short by default and expandable with `--verbose`.

Include mockups for:

- all pass
- derive drift
- ordinary target test failure
- shen typecheck failure
- generated guard audit failure

### 5. Agent-Facing Summary

Design a compact summary for `sb loop`.

It should tell the agent:

- what failed
- what evidence was expected
- where the relevant spec lives
- where the target implementation lives
- what command reproduces the problem

Avoid dumping large JSON into prompts.

### 6. Staging

Propose a staged plan:

- **v0:** emit report from existing gates and derive config.
- **v1:** include symbol-level summaries from shengen and shen-derive.
- **v2:** include links to counterexample artifacts.
- **v3:** include per-premise static/runtime discharge if the proof engine exposes it.

## Guardrails

- Do not claim sampled tests are proofs.
- Do not claim guard constructors prove implementation behavior beyond construction boundaries.
- Do not require Shen in production.
- Do not redesign the manifest format unless absolutely necessary.
- Do not make this depend on a specific LLM harness.
- Keep output deterministic and diffable.

## Deliverable

Write a detailed design document with:

1. Problem statement.
2. Proposed command surface.
3. JSON schema.
4. Human report mockups.
5. Integration points in the current codebase.
6. Staged implementation plan.
7. Risks and mitigations.
8. A walkthrough using `examples/payment/`.
