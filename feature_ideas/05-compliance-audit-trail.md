# Feature Design Prompt: Compliance Audit Trail

You are designing compliance-grade audit artifacts for Shen-Backpressure. This is a design task, not an implementation task. Produce an implementation-ready design document, but do not edit code.

## Context

Shen-Backpressure already creates evidence across several gates:

- Shen spec typechecking.
- shengen generated guard types.
- shen-derive generated oracle tests.
- ordinary target-language tests and builds.
- generated artifact drift/audit checks.
- agent-loop context via `sb context`.

Today that evidence mostly lives in logs and generated files. Regulated or security-sensitive teams need durable artifacts: what spec was checked, what tool version ran, what generated files were produced, what samples were used, which gates passed, and what changed since the previous verified state.

This feature should package verification evidence into stable artifacts suitable for CI, PR review, release archives, SOC 2 controls, internal change-management review, or later cryptographic signing.

## Goal

Design a **Compliance Audit Trail** feature for Shen-Backpressure.

The feature should produce deterministic, reviewable, machine-readable and human-readable artifacts that answer:

- What was verified?
- Against which specs?
- With which tool versions?
- On which source revision?
- With which generated artifacts?
- With which samples/seeds?
- What failed or changed?
- What remains outside the verified boundary?

## Desired User Experience

A user can run:

```bash
sb audit-report --out verification/audit/
sb gates --audit-report verification/audit/current/
sb evidence sign verification/audit/current/evidence.json
```

And commit or upload artifacts like:

```text
verification/audit/current/
  evidence.json
  evidence.md
  evidence-diff.json
  counterexamples.json
  manifest.lock.json
  generated-files.sha256
  commands.log
  summary.md
```

The exact command names are up for design. Keep them consistent with the rest of `sb`.

## Design Requirements

### 1. Artifact Set

Design the audit artifact directory.

At minimum consider:

- `evidence.json` — structured evidence report.
- `evidence.md` — human-readable evidence report.
- `diff.json` — differential verification report when a baseline exists.
- `counterexamples.json` — failing witnesses, if any.
- `manifest.lock.json` — normalized `sb.toml` plus resolved commands and tool versions.
- `hashes.json` — content hashes for specs, generated files, target files, and scripts.
- `commands.log` — commands executed, exit codes, duration, stdout/stderr locations.
- `environment.json` — OS, tool versions, Shen backend, Go/Node versions, relevant env vars.
- `summary.md` — concise reviewer-facing summary.

Explain which artifacts are v0 and which are later.

### 2. Determinism and Diffability

Audit artifacts must be stable.

Design rules for:

- timestamps
- absolute vs relative paths
- command ordering
- JSON key ordering
- environment capture without secrets
- redaction
- generated file hashing
- deterministic sample seeds

Avoid artifacts that churn on every local run without meaningful changes.

### 3. Trust Boundary

Define the trust model.

Questions to answer:

- What does Shen-Backpressure claim?
- What does it not claim?
- Which artifacts are generated by the tool?
- Which files are trusted inputs?
- How are generated files audited?
- How are manual assumptions represented?
- How are external commands treated?

Be explicit: sampled evidence is not a proof, ordinary tests are not formal verification, and target-language deployment does not include Shen unless a project chooses to.

### 4. Signing and Provenance

Design optional signing, but do not require it for v0.

Consider:

- local checksums only
- minisign/cosign integration
- GitHub Actions artifact attestations
- SLSA provenance
- signed `evidence.json`

Recommend a staged path:

- v0: deterministic hashes.
- v1: local signature support.
- v2: CI provenance/attestations.

### 5. CI and PR Integration

Design how audit artifacts are used in CI.

Examples:

- upload `verification/audit/current/` as CI artifact
- fail if evidence regresses
- comment summary on PR
- require human review for new manual assumptions
- require regenerated files to match spec hash

Provide example snippets for GitHub Actions, but keep the feature CI-provider agnostic.

### 6. Human Review Summary

Design `summary.md`.

It should be short and answer:

- commit/revision checked
- specs checked
- gates passed/failed
- verification strengthened/weakened
- counterexamples
- unverified boundaries
- manual assumptions
- reproduction commands

Example:

```markdown
# Shen-Backpressure Audit Summary

Revision: abc123
Specs: specs/core.shen

Result: FAIL

Regressions:
- processable oracle now has 3 failing cases.

Counterexamples:
- balance=0, tx.amount=2.5 expected false, got true.

Reproduce:
- sb gates
- go test ./internal/derived -run TestProcessableSpec/case_014
```

### 7. Regulated-Use Framing

Design this for practical engineering teams, not formal-methods marketing.

Potential users:

- fintech teams with payment/ledger invariants
- healthcare teams with dosage/eligibility rules
- security teams reviewing AI-generated code
- teams needing SOC 2 evidence that generated code was not tampered with

State what the artifact helps with and what it does not replace.

## Guardrails

- Do not claim legal/compliance certification.
- Do not include secrets in artifacts.
- Do not require external signing infrastructure for v0.
- Do not make artifacts too large for normal repos.
- Do not treat an audit artifact as a substitute for human review.
- Do not let the LLM update audit baselines silently.

## Deliverable

Write a detailed design document with:

1. Problem statement and target users.
2. Audit artifact directory layout.
3. JSON schemas for key files.
4. Determinism and redaction rules.
5. Trust boundary explanation.
6. CI/PR workflow.
7. Signing/provenance roadmap.
8. Human summary mockup.
9. Example walkthrough using `examples/payment/`.
10. Risks and mitigations.
